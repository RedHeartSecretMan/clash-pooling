# 设计说明

本文只讲**架构与取舍**。工具内部逻辑见 [clashctl.md](clashctl.md)，
Clash 侧配置结构见 [clash-config.md](clash-config.md)。

## 1. 背景与约束

**订阅只保证节点可用，不保证节点在哪。** 机场会复用节点名把不同落地线路挂在同一批标签下：实测中发现过「美国 01」出口在香港、「加拿大 01–06」出口在法国、「德国 01」出口在美国。按名字分组会把不合规地区的节点塞进 AI 池。

由此得出两条硬约束：

1. **地区归属必须实测**：节点属于哪个地区，只能靠出口 IP 判断。
2. **测量不能放在 Clash 内**：`Script.js` 运行在 Clash Verge 的脚本引擎里，实测只有 `console`，没有 `fetch` / `require` / `process`，无法联网。

因此采用「外部测量 + 内部生成」的两段式结构。

## 2. 分层模型

```
规则  →  服务组（AI / 通用 / 其他）  →  地区池（按实测出口）  →  节点
```

| 层 | 决定什么 | 谁维护 | 是否自动 |
|---|---|---|---|
| 规则 | 域名归属哪一类流量 | `Script.js` 的 `LOCAL-RULES` + 机场规则 | 自动 |
| 服务组 | 这一类流量走哪个地区 | 界面手动切换（`select`） | 手动 |
| 地区池 | 该地区内部用哪个节点 | `url-test` 每 15 分钟探活 | 自动 |
| 节点 | 最终出口 | 内核 | — |

服务组保持手动，是因为「AI 走哪个地区」是策略问题，不该由程序代猜。

## 3. 数据源

| 数据 | 位置 | 生产者 | 变化频率 |
|---|---|---|---|
| 节点与机场规则 | `profiles/<订阅>.yaml` | 机场，Clash Verge 每 24 小时下载 | 每天 |
| 实测清单 `VERIFIED` | `profiles/Script.js` 的标记块 | `clashctl exit-check --refresh` | 订阅变更 / 每天 01:00 |
| 分组与本地规则 | `profiles/Script.js` | 本项目（全局扩展脚本） | 随代码 |
| DNS 覆写 | `profiles/Merge.yaml` | 本项目（全局扩展覆写） | 静态 |

清单格式：

```js
var VERIFIED = {
  "香港 01": ["HK", 210],
  ...
};
```

键是节点名（订阅内唯一标识），值是 `[出口地区代码, 实测延迟 ms]`。

## 4. 地区池

### 4.1 建池规则

| 规则 | 取值 | 说明 |
|---|---|---|
| 建池范围 | 清单里出现的任意地区 | 验证节点数达到 3 个即建池；`PREFER` 决定展示顺序，超过上限时也决定保留哪些 |
| 显示名 | ISO 代码 → 中文对照表 | 264 条，未命中直接显示代码；新增地区无需改代码 |
| 池数量上限 | 8 个 | 超出部分留在「其他」，避免组列表过长 |
| 候选来源 | 清单里 `cc` 匹配、节点仍在订阅中、且不是落地页 | 已下架的排除 |
| 排序 | 实测延迟升序 | 见「两个延迟口径」 |
| 池容量 | 10 个 | `POOL_CAP` |
| 建池阈值 | ≥ 3 个节点 | `MIN_POOL`，不足则节点落「其他」 |
| 池类型 | `url-test` | 探活 `gstatic`，900 秒，tolerance 200 ms，`lazy:false`，连续 2 次失败判死 |
| 互斥 | 一个节点只属于一个地区池 | 进池的节点从「其他」移除 |

### 4.1.1 地区发现

不预设地区名单：脚本遍历实测清单，统计每个出口地区的可用节点数，
达到阈值就建池；显示名取自内置的 ISO 代码→中文表（264 条），表里没有的代码直接显示代码本身。
换订阅后新增的地区会自动成池，无需改代码。

### 4.1.2 落地页节点

机场会把官网、广告、剩余流量之类做成「节点」。判定不用某个机场的名字规则，而是通用特征：
名字里出现 URL、IPv4，或含「官网」「广告」「推广」，就视为落地页。

取舍是**宁可漏过滤，不可误杀**：真正的兜底是测量失败自然排除——落地页节点通常也过不了探活。

### 4.2 两种顺序

| 顺序 | 规则 | 目的 |
|---|---|---|
| 服务组里的成员顺序 | 香港强制第一，其余按「该池最快节点的延迟」升序 | 打开组时默认指向最可能合适的地区 |
| 地区池在配置里的顺序 | 按 `PREFER` 排列，未列出的地区按验证节点数排在后面 | 换订阅时位置稳定，新增地区不会挤乱常用池 |

两者不同是刻意的：成员顺序面向「择优」，池列表顺序面向「位置稳定」。

### 4.3 出口 IP 的稳定性

机场常见做法是让多个节点共用同一个落地出口（同一 IP 段），按延迟排序时会看到若干节点的出口 IP 完全相同。

对使用者的影响：

- 切换节点不一定换 IP，想换 IP 要看 url-test 是否选中了不同出口的节点
- `tolerance 200 ms` 的作用就是压制抖动：新节点要比当前快 200 ms 以上才切换，避免池内反复跳动导致出口 IP 频繁变化
- 如果确实需要固定出口，用 `clashctl use <服务组> <具体节点>` 钉死，而不是指望池

## 5. 服务组

| 组 | 默认 | 成员（按顺序） |
|---|---|---|
| `AI` | 延迟最低的非香港池 | 各池按最快节点延迟升序（不含香港），然后 其他、DIRECT、REJECT |
| `通用` | 香港池 | 香港池在最前，其余池按延迟升序，然后 其他、DIRECT、REJECT |
| `其他` | 首个池外节点 | 池外且实测通过的节点、DIRECT、REJECT |

`select` 组默认用第一个成员，而成员顺序按实测延迟排，所以「默认」会随测量结果变化——
上表写的是选择规则，不是固定的地区顺序。

三条设计约束：

1. **AI 组不含香港**。AI 服务的官方支持地区都不含香港，从成员列表里去掉，而不是靠使用者记住。
2. **通用组承接所有兜底流量**（`MATCH`、机场「漏网之鱼」），因此必须包含地区池，否则兜底流量会被钉死在单个节点上。
3. **其他组不参与任何规则**。它的作用是手动指定冷门节点：先 `use <服务组> 其他`，再 `use 其他 <节点名>`。

## 6. 规则

### 6.1 本地规则（仓库 75 条，本机覆盖后约 77 条）

| 目标 | 条数 | 内容 |
|---|---|---|
| `AI` | 36 | OpenAI、Anthropic、Google Gemini、Cursor、Perplexity、Copilot、HuggingFace 及 AI 杂项 |
| `通用` | 15 | Google 日常域（9）、流媒体长尾（6） |
| `DIRECT` | 20 | Microsoft、Google 直连例外（内网规则放在本机覆盖里） |
| `REJECT` | 4 | Google 遥测拦截 |
| `其他` | 0 | 纯兜底 |
| **合计** | **75** | 本机覆盖 `clash/local/rules.local.js` 会注入私有规则并排在最前 |

**没有硬约束例外规则。** AI 组本身不含香港，因此 `cloudcode-pa`、`generativelanguage` 这类「不能走香港」的接口直接指向 AI 组即可，不需要单独指向某个地区池。

### 6.2 顺序依赖

规则自上而下首条命中，以下顺序不能改：

| 依赖 | 后果 |
|---|---|
| 公司内网必须最先 | 否则被后面的代理规则截走 |
| Google 直连例外早于 `google.com` | 否则 `dl.google.com` 被代理 |
| `*.l.google.com` 遥测拦截早于 `google.com` | 否则机场的 REJECT 规则失效 |
| Microsoft 段晚于 AI 段 | 否则 `copilot.microsoft.com` 被一起直连 |

### 6.3 机场规则重映射

机场规则里的组名（`🔰 手动选择`、`🌍 主流媒体`、`🐟 漏网之鱼` 等）由 `RENAME` 表映射到本方案的组；
不认识的目标按语义兜底：含「拦截/广告/Block」→ `REJECT`，含「直连/Direct」→ `DIRECT`，
含地区线索 → 对应地区池（该地区没建池则回落 `通用`），其余 → `通用`。

## 7. 调度

| 定时器 | 时间 | 条件 | 动作 |
|---|---|---|---|
| `refresh-daily` | 每天 01:00 | 无条件 | 全量核验；清单有变化才重启 Verge |
| `refresh-watch` | 每小时，跳过 01:00 | 订阅版本变了 | 全量核验；清单有变化才重启 Verge |
| `refresh-watch` | 每小时，跳过 01:00 | 订阅没变 | 只补测清单里缺失的节点 |

判断依据是 marker 里的**订阅版本戳**：只有全量核验才推进它。这样订阅更新一定会被识别，而增量与抽查不会污染它。

两个任务互斥由锁文件保证（`~/.clash-pooling/refresh.lock`），避免并发起两个临时实例。

## 8. 决策记录

| 决策 | 备选 | 结论与理由 |
|---|---|---|
| 地区归属靠实测而非节点名 | 按名字前缀分组 | 名字不可信，实测可复核 |
| 池成员只收验证过的节点 | 未知节点也进池 | 宁可池小，不可用错地区 |
| AI 组剔除香港 | 允许切香港 | 合规是硬约束，不给误操作的入口 |
| 池 `url-test` 而非 `fallback` | 顺序 + 存活判定 | 节点劣化能被自动替换，无需人工重排 |
| 服务组 `select` 而非 `fallback` | 自动级联 | 切地区是策略，必须可控 |
| 不设独立「手动」组 | 单独收纳组 | 与「其他」职责重叠，合并可少一个组 |
| 取消「超 24 小时触发增量」 | 保留 | 与每日全量重复，且会和全量抢同一个判断导致全量被跳过 |
| 硬约束例外规则全部删除 | 7 条例外指向美国池 | AI 组已不含香港，例外失去意义 |
| 地区池自动发现 | 写死地区名单 | 换订阅不必改代码；`PREFER` 决定展示顺序与超限时的取舍 |
| 私有配置分离到 `clash/local/` | 内网规则直接进仓库 | 仓库可公开，本机行为不变；`sync` 时注入 |

## 9. 两个延迟口径

| 指标 | 测量者 | 连接状态 | 用途 | 典型值 |
|---|---|---|---|---|
| cloudflare TTFB | `clashctl exit-check` | 每次新建（DNS+TCP+TLS） | 分类、池内排序 | 香港 209 ms、新加坡 1341 ms |
| gstatic delay | 内核 `url-test` | 复用已建隧道 | 池内实时择优 | 同节点 40~223 ms |

同一节点实测：curl 冷连接测 cloudflare 2.4 s、gstatic 1.6 s（目标差异次要），而 `url-test` 报 160 ms——**量级差异来自冷热连接，不是目标网站**。

结论：清单延迟只能判断相对快慢，不能当用户感受读；最终选谁由 `url-test` 决定。
