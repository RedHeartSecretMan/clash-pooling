# clashctl 逻辑

## 1. 它为什么存在

Clash Verge 的扩展脚本运行在沙箱里：没有 `fetch`、没有 `require`、没有文件读写。它只能拿现成的 `config` 对象做变换。

这意味着**「这个节点出口在哪个地区」这件事在 Clash 内部无法得知**。`clashctl` 就是补这一块的：它在 Clash 之外测量，把结果写成 Clash 能读的数据。

```
clashctl（外部，能联网）         Script.js（Clash 内，不能联网）
  实测每个节点的出口地区    →    读取清单，按出口分池
```

## 2. 命令分层

| 层 | 命令 | 是否改变状态 |
|---|---|---|
| 查看 | `status` `regions` `nodes` `test` | 只读 |
| 操作 | `use` `sync` | 改分组选中 / 改配置 |
| 核验 | `exit-check` `auto` | 改清单、可能重启 Verge |
| 维护 | `audit` `doctor` `backup` | 只读或写备份 |

与内核的交互不依赖界面：macOS 走 unix socket，Windows 走 `external-controller` 的 TCP 地址，
两者的地址与密钥都从生成后的配置里读取。

## 3. 核验流水线

`clashctl exit-check --refresh` 的完整流程：

```
1. 取节点清单（内核 API），剔除落地页/广告节点
2. 判断模式
     显式 --full        → 全量
     订阅版本变了        → 全量（机场可能改线路，旧标签不可信）
     否则               → 增量：只测清单里没有的节点
3. 起临时 mihomo 实例（独立端口 17981/18181，不碰生产）
4. 逐节点测量（见下）
5. 合并结果：旧清单里仍存在且本次没测的保留；测过的覆盖；测失败的删除
6. 写回 Script.js 的 VERIFIED 块
7. 更新 marker（只有全量才推进订阅版本戳）
8. 若清单有变化：定时任务会自动重启 Clash Verge；手动执行时只提示，需自己重启
```

### 单节点测量的四道保险

| 保险 | 做法 | 防的事故 |
|---|---|---|
| 确认切换 | PUT 后轮询组状态，直到 `now` 等于目标节点 | 切换未生效就读到上一个节点的出口 |
| 稳定等待 | 确认后再等 0.6 秒 | `now` 变了但旧连接还在用 |
| 双探测 | 第一次成功后复测一次，两次地区不一致则丢弃 | 节点抖动导致错误标签 |
| 超时上限 | 单节点 7 秒（快速模式），整轮 3000 秒 | 卡死节点拖垮整轮 |

### 三种模式

| 模式 | 触发 | 测多少 | 耗时 |
|---|---|---|---|
| 全量 | `--full` 或订阅变更 | 全部节点 | 10~15 分钟 |
| 增量 | `--refresh` 且订阅未变 | 清单里缺失的节点 | 秒级~1 分钟 |
| 抽查 | `--recheck <子串>` | 名字匹配的节点 | 取决于数量 |

抽查**永远不算全量**：它不会推进订阅版本戳，否则过期标签会被洗白。

## 4. marker 语义

`~/.dsh-clashctl/last-refresh` 记录：

```json
{"verified_at": "...", "profile_mtime": 1794362271,
 "verified_count": 71, "node_count": 72, "last_full": false}
```

`profile_mtime` 表示「整份清单是针对哪个订阅版本验的」。**只有全量核验才推进它**——增量与抽查都不许动。这样：

- 订阅更新 → 版本戳落后 → 一定被识别为「需要全量」
- 增量补测 → 版本戳不变 → 不会被误判成「已按新订阅验过」

## 5. 定时调度

| 任务 | 时间 | 条件 | 动作 |
|---|---|---|---|
| `refresh-daily` | 每天 01:00 | 无条件 | 全量核验 |
| `refresh-watch` | 每小时，跳过 01:00 | 订阅变了 | 全量核验 |
| `refresh-watch` | 每小时，跳过 01:00 | 订阅没变 | 增量补测死节点 |

锁文件 `~/.dsh-clashctl/refresh.lock` 保证同一时刻只有一个核验在跑（陈旧锁超过 3 小时自动清理）；
核验结束后若清单没变化则不重启 Verge。

## 6. 失败处理

| 情况 | 行为 |
|---|---|
| 端口被占 | 直接报错退出，不写清单（避免写出全是「失败」的结果） |
| 超过总时长上限 | 停止并标记不完整，**不推进订阅版本戳** |
| 节点探测失败 | 从清单移除，节点落「其他」或不出现 |
| 清单未变化 | 跳过重启 |

## 7. 代码结构

```
bin/clashctl                 启动器（Python）：把 ../lib 加入 sys.path 后进入 CLI
bin/clashctl.cmd             Windows 启动器：定位 Python 后调用同一个脚本
lib/clashctl/
  __main__.py                参数分派
  commands.py                各子命令实现
  measure.py                 测量流水线（临时实例、切换、探测）
  probe.py                   HTTP 探测（标准库，不依赖 curl）
  api.py                     mihomo 控制接口（unix socket / TCP）
  platform.py                平台差异：路径、端点、内核、重启、调度
  scheduler.py               定时核验：launchd / 任务计划程序
  manifest.py                清单解析、增量决策、块替换（纯函数）
tests/                       三个缝：Script.js 分组逻辑、manifest 纯函数、敏感内容扫描
```

全部逻辑用 Python 标准库实现，macOS 与 Windows 共用同一份代码。
平台差异主要收在 `platform.py`；唯一例外是 `scheduler.py`，因为 launchd 与任务计划程序的
注册方式本质不同，那里按平台分叉。
清单相关逻辑单独放在 `manifest.py`，因为它决定「哪些节点要测」「清单怎么写回」，出错会静默污染数据。
